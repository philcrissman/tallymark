Deploy Tallymark to AWS

This guide takes you from nothing to a working dashboard. If you already use AWS, expect about ten minutes. If you're starting fresh, setting up credentials adds about fifteen more.

What gets deployed

One CloudFormation stack, defined in infra/template.yaml, creates:

ResourceWhat it's for
API Gateway (REST)The public /track endpoint, plus /stats and /sites, which need your API key
Lambda functionThe Haskell backend: a single static binary on the provided.al2023 runtime
DynamoDB tablePage views, billed per request. It is kept if the stack is deleted, so you can't lose data by accident.
S3 bucketHosts the static dashboard as a website

Prerequisites

To deploy a release bundle (recommended), you need:

  • An AWS account
  • AWS CLI v2
  • AWS SAM CLI

To build from source, you also need:

  • Docker. The backend is compiled inside a GHC/musl container, so you don't need a local Haskell toolchain.
  • Elm 0.19.1, for example via npm install -g elm. terser is optional and used for minifying.
  • make and zip

Check the tools are installed:

aws --version
sam --version

Set up AWS credentials

The deploy script uses whatever credentials the AWS CLI is set up with. If aws sts get-caller-identity already prints your account, skip to the next step.

The simplest secure setup is IAM Identity Center (SSO):

aws configure sso
# follow the prompts, then:
export AWS_PROFILE=your-profile-name
aws sts get-caller-identity

What permissions are needed? The deploying user needs to create CloudFormation stacks, IAM roles (for the Lambda function), Lambda functions, API Gateway APIs, DynamoDB tables and S3 buckets. AdministratorAccess on a personal account is simplest. In a shared account, ask your admin for a role covering those services.

Get Tallymark

Option A: download a release (no build needed)

Each GitHub release includes a bundle with the compiled Lambda function, the built dashboard, the template and the deploy script.

curl -LO https://github.com/philcrissman/tallymark/releases/latest/download/tallymark.tar.gz
tar xzf tallymark.tar.gz
cd tallymark-*

Option B: build from source

git clone https://github.com/philcrissman/tallymark.git
cd tallymark
make build

make build compiles the backend in Docker (the first build takes 15–30 minutes while dependencies compile; later builds are quick), producing backend/build/function.zip. It also compiles the dashboard into dashboard/build/.

Apple Silicon: the build uses --platform linux/amd64 to produce an x86_64 Lambda binary. It works on ARM Macs through emulation, just more slowly.

Configure

Copy the example settings file. tallymark.env is git-ignored, so your key stays out of version control.

cp tallymark.env.example tallymark.env

Generate an API key. You'll type it into the dashboard to sign in.

openssl rand -hex 32

Then edit tallymark.env:

TALLYMARK_API_KEY=paste-your-generated-key-here
TALLYMARK_ALLOWED_SITES=example.com,blog.example.com
TALLYMARK_STACK_NAME=tallymark
TALLYMARK_REGION=us-east-1
SettingDefaultMeaning
TALLYMARK_API_KEYrequiredBearer token for the dashboard and the stats API
TALLYMARK_ALLOWED_SITESempty (accept all)Comma-separated site IDs that /track accepts. Page views for any other site ID get a 403.
TALLYMARK_STACK_NAMEtallymarkCloudFormation stack name. Use a different one per deployment.
TALLYMARK_REGIONus-east-1AWS region to deploy into
TALLYMARK_TABLE_NAMEgeneratedOptional fixed DynamoDB table name, for adopting an existing table
TALLYMARK_DASHBOARD_BUCKETgeneratedOptional fixed S3 bucket name. It must be globally unique.

A site ID is any label you like. Your domain name is the obvious choice. It's what the dashboard's site picker shows.

You can also set any of these as environment variables instead of using the file, for example in CI.

Deploy

./scripts/deploy.sh      # release bundle, or source after `make build`
make deploy              # from source: builds, then deploys

The script:

  1. Runs sam deploy to create or update the stack. SAM makes a small bucket for deployment artifacts the first time.
  2. Reads the stack outputs and writes your API URL into the dashboard's config.js.
  3. Uploads the dashboard to the S3 bucket.
  4. Prints your API endpoint and dashboard URL.
==> Deploy complete!

  API endpoint:  https://a1b2c3d4e5.execute-api.us-east-1.amazonaws.com/prod
  Dashboard:     http://tallymark-dashboardbucket-xxxx.s3-website-us-east-1.amazonaws.com

Add the tracker to your site

Open the dashboard URL and sign in with your API key. Click Get Tracker Code and paste the snippet into every page, either in <head> or just before </body>. The snippet looks like this:

<script>
(function() {
  "use strict";
  var endpoint = "https://YOUR-API-ID.execute-api.us-east-1.amazonaws.com/prod/track";
  var siteId = "example.com";
  if (navigator.doNotTrack === "1") return;
  if (document.visibilityState === "prerender") return;
  var data = JSON.stringify({
    url: window.location.pathname,
    referrer: document.referrer || null,
    siteId: siteId
  });
  if (navigator.sendBeacon) {
    navigator.sendBeacon(endpoint, data);
  } else {
    var xhr = new XMLHttpRequest();
    xhr.open("POST", endpoint, true);
    xhr.setRequestHeader("Content-Type", "text/plain");
    xhr.send(data);
  }
})();
</script>

Before you have a site in the dashboard, its picker is empty. The snippet then uses your-site.com, so change siteId to one of your allowed sites. The site shows up in the dashboard after its first page view.

Hugo

Put the snippet in a partial such as layouts/partials/analytics.html, and wrap it so hugo server doesn't count your own visits:

{{ if not hugo.IsServer }}
  <script> ...snippet... </script>
{{ end }}

Jekyll, Eleventy, Astro and others

Add the snippet to your base layout. To skip local development, check the environment: jekyll.environment == "production" in Jekyll, import.meta.env.PROD in Astro, and so on.

Check that it works

Send a test page view straight to the API:

API=https://YOUR-API-ID.execute-api.us-east-1.amazonaws.com/prod

curl -X POST "$API/track" \
  -d '{"url":"/hello/","referrer":null,"siteId":"example.com"}'
# {"ok":true}

curl -H "Authorization: Bearer $TALLYMARK_API_KEY" \
  "$API/stats?site=example.com&start=$(date +%Y-%m-%d)&end=$(date +%Y-%m-%d)"

Refresh the dashboard and pick Today. You should see the view. Then load a page of your real site, ideally in a browser without an ad blocker, and check that it's counted too.

Updating and rotating keys

Update to a new version

Download the new release (or git pull && make build), copy over your tallymark.env, and run ./scripts/deploy.sh again. Updates happen in place and your data stays put.

Rotate the API key

Change TALLYMARK_API_KEY in tallymark.env and redeploy. The old key stops working right away, so sign in to the dashboard again with the new one.

Add or remove a site

Edit TALLYMARK_ALLOWED_SITES and redeploy. To delete all stored data for a site:

curl -X DELETE -H "Authorization: Bearer $TALLYMARK_API_KEY" "$API/sites?site=old-site.com"

Adopting an existing deployment

If you deployed an early version that used fixed resource names, set TALLYMARK_STACK_NAME, TALLYMARK_TABLE_NAME and TALLYMARK_DASHBOARD_BUCKET to your existing names. CloudFormation then updates the stack in place and doesn't replace your table.

What it costs

Tallymark has no servers sitting idle, so you pay only for requests. Each page view is one API Gateway request, one short Lambda invocation and a few small DynamoDB writes. For a personal site with tens of thousands of page views a month, the bill is typically well under a dollar, and much of it may fall within the AWS free tier. Check the current API Gateway, Lambda and DynamoDB pricing for your region.

Tip: set an AWS Budget alert of a few dollars a month. It's good practice for any personal AWS account.

Security notes

  • /track is public by design, because browsers have to reach it. The allowlist rejects page views for unknown site IDs, but anyone who reads your snippet could still send fake views for your site. That's true of every client-side analytics tool.
  • The dashboard is served over plain HTTP from the S3 website endpoint. Its calls to the API go over HTTPS, but the page itself could be tampered with on a hostile network. For HTTPS, put CloudFront (or another CDN) with a custom domain in front of the bucket.
  • The API key is the only credential. Use a long random value, keep tallymark.env private, and rotate the key if it leaks. The dashboard keeps it in sessionStorage only, so it's cleared when the tab closes.

Uninstalling

# Empty the dashboard bucket, then delete the stack
aws s3 rm "s3://$(aws cloudformation describe-stacks --stack-name tallymark --region us-east-1 \
  --query "Stacks[0].Outputs[?OutputKey=='DashboardBucketName'].OutputValue" --output text)" --recursive
sam delete --stack-name tallymark --region us-east-1

The DynamoDB table is kept on purpose. When you're sure you don't need the data, delete it in the AWS console or with aws dynamodb delete-table.

Troubleshooting

SymptomLikely cause
Dashboard says "unauthorized"Wrong API key, or you rotated it. The dashboard goes back to the sign-in screen, so enter the current key.
/track returns 403 "unknown site"The snippet's siteId isn't in TALLYMARK_ALLOWED_SITES. Add it and redeploy.
No views from your own browserDo Not Track is on, or an ad blocker is blocking the request. Try a private window with extensions off.
Dashboard is blank or can't reach the APIconfig.js wasn't written. Re-run ./scripts/deploy.sh, or open the dashboard with ?api=https://your-api-url/prod.
sam deploy fails creating the bucketTALLYMARK_DASHBOARD_BUCKET is set to a name that's already taken globally. Clear it to get a generated name.
Deploy script can't find function.zipRun make build-backend, or download function.zip from a release into backend/build/.

Local development

You can run the whole stack locally with DynamoDB Local and sam local:

make local-setup     # DynamoDB Local in Docker + create the table
make local-seed      # ~70 sample page views for example.com
make local-api       # build the backend and serve it on :3000

# in another terminal
make build-dashboard
cd dashboard/build && python3 -m http.server 8080

Open http://localhost:8080/?api=http://localhost:3000 and sign in with localdevkey.

Other platforms

Tallymark runs on AWS today. The backend is a single static binary, so other platforms are possible. Two pieces are tied to AWS: the Lambda runtime adapter and the DynamoDB storage layer.

AWS Supported

Lambda + API Gateway + DynamoDB + S3, as described above.

Azure Planned

Azure Functions supports custom handlers: any executable that serves HTTP. Porting needs an HTTP server mode for the backend and a Table Storage or Cosmos DB storage layer. The dashboard could go on Static Web Apps.

Ubicloud & plain VMs Idea

Ubicloud offers VMs, managed PostgreSQL and Kubernetes, but no Lambda-style functions. The natural fit is a long-running server with a PostgreSQL or SQLite backend, which would also work on any VPS or homelab.
